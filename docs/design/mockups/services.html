General settings are not drawn in this mockup. The five v0.1 screens are the scope.

Only the system tag namespaces ship in v0.1: type:, format:, source:, quality:, indexer:. They render as chips you can filter by but not delete. A tag is not a library: a library is a single-kind container with sources and a destination, a tag is a cross-kind label, and a saved filter is a query. Aliases, virtual parents, the rule engine and saved filters are v1.0.

Theme and density live in the top bar of every screen, and both persist. There is no colour-impaired mode setting, because every status here is an icon and a word as well as a colour — including the availability tick and cross, whose word is read out rather than shown, because the column header already says which quality it is about.

WCAG 2.2 SC 2.1.4 is a Level A criterion and it is satisfied by exactly one of three things: the shortcut can be turned off, it can be remapped, or it is active only on focus. "It also has a visible mouse equivalent" is not one of them — the criterion exists for speech-input users, whose dictation is typed into the page, and for anyone with a tremor. This switch is the "turn off", it covers /, l, j, k and ?, and it persists. Shortcuts that need a modifier are unaffected.

A 404 from an HTML server, rather than a refused connection, means something answered but it was not Sonarr. The three usual causes, in the order they happen:

  • A missing URL base. A reverse proxy serving Sonarr at /sonarr needs that path in the base URL. This is the most common one on a Tailscale or nginx install.
  • The wrong kind. Sonarr and Radarr both answer /api/v3/system/status, so a Radarr URL under the Sonarr kind connects and then reports the wrong application. The success panel names what answered for exactly this reason.
  • The browser's address rather than this host's. UsArr calls the service from the container it runs in, not from your browser.
